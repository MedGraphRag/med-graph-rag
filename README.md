# MedGraphRAG

GraphRAG по клиническим рекомендациям Минздрава РФ. Архитектура и ограничения описаны в [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md).

## ГРЛС: установка и запуск

Python 3.11+, httpx, Polars и Pydantic v2. Из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m src.nlp.grls_scraper --page-size 100
# Ограниченная диагностическая выгрузка:
python -m src.nlp.grls_scraper --max-pages 2
# Необязательный повторяющийся фильтр (значения уточняются в реестре):
python -m src.nlp.grls_scraper --condition-id STATUS_1 --condition-id STATUS_2
python -m src.nlp.grls_etl --input-dir data/raw/grls/snapshot_TIMESTAMP --repair-mojibake --allow-incomplete
```

Без `--input-dir` ETL выбирает последний snapshot. `--allow-incomplete` явно разрешает диагностическую обработку неподтверждённой выгрузки; без него требуется `complete=true` в manifest после внешней проверки покрытия. Не выставляйте этот признак только по пустой странице.

Загрузчик последовательно запрашивает страницы с 1, по 100 объектов, с задержкой 0.25 секунды (`--delay`). Повторяет запросы после 429, 5xx и сетевых тайм-аутов. Cookies и авторизация не используются. Ответы сохраняются как полученные httpx байты тела (после транспортной декомпрессии), без перекодировки, в `data/raw/grls/snapshot_*/pages/page_*.json`. Непустая короткая страница не останавливает пагинацию. Повтор страницы, отсутствие новых идентификаторов или страница, где у всех объектов нет одновременно lpId и торгового названия, останавливает загрузку как неполную. Manifest обновляется во время работы; Ctrl+C отмечается как `interrupted`.

Проверка manifest:

```bash
python -m json.tool data/raw/grls/snapshot_TIMESTAMP/manifest.json
```

Проверяйте `termination_reason`, `pagination_complete`, `complete`, `coverage_verified`, счётчики полученных/уникальных записей, `condition_id_counts`, `errors`, `response_encodings`. Проверяйте также `quality_issue` и `api_total_count_initial`: счётчик API может быть нестабильным. `valid_utf8` проверяет байты, а не смысл строк: корректный UTF-8 тоже может содержать mojibake. Пустая страница подтверждает только завершение наблюдаемой пагинации. Отсутствие фильтра статусов не доказывает покрытие всех категорий; нужна внешняя сверка с интерфейсом и итогами реестра. Автоматически `complete` и `coverage_verified` остаются false.

## Результаты ETL

* `data/processed/grls_normalized.parquet`: `trade_name_norm`, `inn_norm`, `atx_code` (список строк).
* `data/processed/grls_normalized_records.parquet`: минимальное происхождение — lpId, ruNumber, исходные/исправленные имена, массивы mnnCode и atx, conditionId, JSON лекарственных форм. При `--output` имя второй таблицы получает суффикс `_records`.

Polars приводит названия к нижнему регистру, удаляет дозировки, скобочные фрагменты, распространённые формы и повторные пробелы, затем удаляет дубликаты и сортирует результат. Комбинированные МНН не разбиваются на неподтверждённые связи с АТХ. `mnnName="~"` становится null, исходный текст сохраняется. Производители, инструкции и прочие тяжёлые поля остаются только в raw. Исходные страницы ETL не изменяет. Повреждённые страницы блокируют запись результата.

`--repair-mojibake` пробует обратимое CP1251 → UTF-8 преобразование только при признаках повреждения и уменьшении их числа. Проверены примеры из патча и сгенерированные варианты. Позднее выполнены ограниченные живые запросы для диагностики пагинации; результаты описаны ниже.

## Проверки

```bash
python -m compileall -q src tests
python -m pytest -q
python -m unittest discover -s tests -p 'test_grls_pipeline.py' -v
```

Тесты используют мокированный HTTP. Поиск кардиологических названий проверяется на фикстурах. Критерии <10 секунд и <30 МБ для всей базы требуют замера на полном подтверждённом JSON snapshot; наличие исходных XLSX не подтверждает эти критерии для API-пайплайна. Старые XLSX этот загрузчик и ETL не изменяют и не обрабатывают.

Замер интеграции: синтетические 60 000 записей в 600 JSON-страницах — 1.081 с на ETL с записью обеих таблиц, основной Parquet 32 399 байт. Искусственные данные хорошо сжимаются; результат не является проверкой критериев на реальной базе.

## Известная проблема API (16 октября 2026)

Сайт по умолчанию использует статусы `Д` и `П`, что объясняет 16585 элементов в интерфейсе против другого количества в API без фильтра. Но и с этим фильтром на странице 101 (size=100) API отдаёт объекты без lpId, торгового названия и АТХ. За объявленным концом выборки API продолжает отдавать неполные объекты и меняет x-total-count. Загрузчик теперь останавливается как `unusable_page`; ETL не пропускает такую страницу только по флагу `--allow-incomplete`; для явно частичного справочника из пригодных записей добавьте `--mapped-only`. Старую выгрузку с этим дефектом нельзя считать полной или нормализовать с молчаливым отбрасыванием строк. Подробности и проверенные числа — [диагностика API](docs/grls_api_diagnostics.md).

## Частичный справочник только с заполненной связью

Для существующей выгрузки с неполными объектами можно явно выбрать только записи с непустыми нормализованными торговым названием, МНН и списком АТХ:

```bash
python -m src.nlp.grls_etl \
  --input-dir data/raw/grls/snapshot_20261016T105630721477Z \
  --output data/processed/grls_mapped_candidate.parquet \
  --repair-mojibake --allow-incomplete --mapped-only
```

`--mapped-only` пропускает целиком страницы, где нет ни одной записи с заполненными исходными торговым названием, МНН и АТХ. На смешанных страницах сохраняет пригодные связи, исключая неполные строки из поискового справочника. Массивы кодов не разворачиваются в неподтверждённые пары. Валидированные записи с оставшихся страниц после дедупликации по lpId сохраняются в `_records.parquet`. Полностью пропущенные страницы остаются только в исходных JSON, которые не изменяются. `_report.json` содержит число входных объектов, список пропущенных страниц (`skipped_page_files`), количество объектов на них (`skipped_page_records`), исключения на оставшихся страницах (`excluded_records`), общую сумму исключений (`total_excluded_records`) и число итоговых строк. Счётчики отсутствующих полей относятся к оставшимся после пропуска страниц записям после дедупликации по lpId и могут пересекаться. `source_complete=false` отражает неподтверждённое покрытие исходного snapshot. Режим не исправляет серверную пагинацию и не подтверждает актуальность статуса каждой записи; в этой выгрузке много записей со статусом «Измененный». Некорректный JSON и неизвестная схема по-прежнему блокируют обработку. При повторном запуске указанные выходные файлы перезаписываются.

## Объединение нескольких snapshot

ETL поддерживает повторяющийся `--additional-input-dir`. Укажите первоначальную и целевую выгрузки явно:

```bash
python -m src.nlp.grls_etl \
  --input-dir data/raw/grls/snapshot_ORIGINAL \
  --additional-input-dir data/raw/grls/snapshot_ACTIVE \
  --output data/processed/grls_normalized.parquet \
  --repair-mojibake --allow-incomplete --mapped-only
```

Связи из всех источников объединяются и дедуплицируются. `lpId` дедуплицируется внутри каждого snapshot; наблюдения из разных snapshot сохраняются отдельно с `source_snapshot` и `source_page` в `_records.parquet`, поэтому новый статус не затирает историю. Отчёт содержит статистику каждого источника и `new_links_added` относительно первого snapshot. Это число новых связей, а не новых лекарственных препаратов. Все источники проходят валидацию до замены выходных файлов. Повторное указание одного snapshot не дублирует источник. Пустые поля и статусы не восстанавливаются догадками; покрытие всего реестра по-прежнему не подтверждено.

### Текущий объединённый результат

16 октября 2026 выполнена целевая загрузка `Д`/`П`: `snapshot_20261016T130852032029Z`, 100 страниц, 10000 уникальных записей (9933 `Д`, 67 `П`), без ошибок. Причина остановки — `max_pages_reached`, полнота не подтверждена. Объединение с первоначальным snapshot дало 8369 связей (+3883 к 4486), основной файл 125351 байт; ETL с запуском Python занял 2.252 секунды. Старые связи и raw сохранены. Таблица происхождения содержит 20000 наблюдений с привязкой к источнику.

Для воспроизведения именно объединённого справочника:

```bash
python -m src.nlp.grls_etl \
  --input-dir data/raw/grls/snapshot_20261016T105630721477Z \
  --additional-input-dir data/raw/grls/snapshot_20261016T130852032029Z \
  --output data/processed/grls_normalized.parquet \
  --repair-mojibake --allow-incomplete --mapped-only
```

Запуск ETL только на одном snapshot перезапишет результат выборкой одного источника. Для сохранения объединения указывайте оба snapshot, как выше. Резервная копия перед объединением находится в `data/processed/backups/grls-before-active-merge-20261016T131040524080Z/`.

## Полная выборка Д/П с проверкой покрытия

Для основного справочника актуальных записей используйте отдельный сборщик:

```bash
SSL_CERT_FILE="$HOME/Downloads/Russian_Trusted_CA.pem" \
  python -m src.nlp.grls_active --delay 1
```

Он не ограничивает выгрузку первыми 100 страницами: разбивает запрос Д/П по датам регистрации (по умолчанию до 2024 года, 2024 год и с 2025 года). Для каждой части страницы запрашиваются последовательно с 1. Часть завершается при совпадении уникальных записей со стабильным `x-total-count`; изменение счётчика, повторы или непригодные страницы не считаются успехом. При изменении размера выборок можно задать больше границ повторяющимся `--split-date YYYY-MM-DD`.

В `data/raw/grls/collection_active_*/` сохраняются исходные части, контрольные ответы и отчёт сборки. Обычный итоговый `snapshot_*` публикуется только после проверок:

* До и после загрузки общий счётчик Д/П совпадает.
* Число уникальных непустых lpId равно этому счётчику и сумме размеров частей.
* У всех объектов состояние Д или П; контрольные записи присутствуют.
* Исходные тела ответов скопированы без изменения байтов, SHA-256 проверены. Manifest сохраняет происхождение каждой страницы.

`complete=true` и `coverage_verified=true` итогового snapshot относятся **только к запросу Д/П** (`coverage_scope=conditionIds=Д,П`). `registry_complete=false`: другие состояния реестра в эту выгрузку не входят. Это проверка покрытия относительно текущих ответов API, а не независимая выгрузка всех категорий ГРЛС.

Сборщик напечатает точный путь итогового snapshot. Нормализация этого snapshot:

```bash
python -m src.nlp.grls_etl \
  --input-dir data/raw/grls/snapshot_VERIFIED_D_P \
  --output data/processed/grls_normalized.parquet \
  --repair-mojibake --mapped-only
```

Здесь `--allow-incomplete` не требуется. Все записи Д/П, включая не имеющие АТХ, сохраняются в raw. Основной поисковый Parquet содержит только заполненные связи, поэтому его количество строк будет меньше числа регистрационных записей. ИЗМ/ИСКЛ из предыдущего объединённого справочника в новую основную таблицу не переносятся; прежние результаты сохраняются в backups перед заменой.
