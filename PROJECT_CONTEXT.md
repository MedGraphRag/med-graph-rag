## 2. Архитектура и стек технологий

Проект пишется на **100% чистом Python 3.11+**. Нативные компилируемые языки (C / C++) исключены из архитектуры.

```text
[ cr.minzdrav.gov.ru (КР) ] ──> [ ТРЕК 1: Data & NLP ] ──> Извлечение триплетов (Instructor)
[ rlp.minzdrav.gov.ru (API ГРЛС, Д/П) ] ──> [ raw snapshots + проверка покрытия ]
          └──> [ Pydantic v2 + Polars: grls_normalized.parquet ] ──> Entity Resolution (Sentence-Transformers)
                                                                        │
                                                                        ▼
                                                         [ ТРЕК 2: Knowledge Graph ]
                                                         • СУБД: Neo4j (Docker, Cypher)
                                                         • Транзитивный вывод по МКБ-10
                                                         • Поиск межлекарственных пересечений (DDI)
                                                                        │
                                                                        ▼
                                                         [ ТРЕК 3: Multi-Agent & UI ]
                                                         • Multi-Agent Debate (LangGraph)
                                                         • Оценка метрик (Ragas)
                                                         • Интерфейс (Streamlit)
```

### Стек компонентов:
* **База данных онтологии:** **Neo4j** (Community Edition 5.x в Docker Compose, плагины APOC и Graph Data Science).
* **Инженерия данных и ETL:** `httpx` (асинхронные запросы), `polars` (обработка таблиц ГРЛС), `trafilatura` / `beautifulsoup4` (парсинг HTML), `PyMuPDF` (парсинг PDF).
* **NLP и онтологическое моделирование:** `instructor`, `pydantic` (v2), `sentence-transformers` (модель `all-MiniLM-L6-v2`), `owlready2` (экспорт в OWL).
* **Инференс нейросетей:** `openai` Python SDK через переменные `LLM_BASE_URL` и `LLM_API_KEY` (облачный Groq API: `llama-3.3-70b-versatile`, резерв: DeepSeek-V3 или локальная Ollama).
* **Оркестрация агентов:** **LangGraph** (детерминированная стейт-машина дебатов `StateGraph`).
* **Бенчмаркинг качества:** **Ragas** (метрики Faithfulness, Context Recall).
* **Пользовательский интерфейс:** **Streamlit**.

## 4. Жесткие правила и ограничения (Architectural Invariants)

1. **Запрет на C / C++:** Никаких нативных компилируемых вставок. Архитектура не должна усложняться вызовами FFI/ctypes.
2. **Нулевые галлюцинации (Zero-Hallucination Policy):**  
   Нейросеть не имеет права давать клинические рекомендации из своей памяти. Все ответы формируются **исключительно как трансляция связей подграфа Neo4j**. Температура генерации $T = 0.0$.
3. **Строгая типизация (Pydantic Enforcement):**  
   Запрещен обмен сырыми словарями `dict` без валидации. Все сущности и состояния агентов валидируются через `pydantic.BaseModel`.
4. **Правовой статус (323-ФЗ и 152-ФЗ):**  
   * Система является **информационно-поисковым сервисом**, а не медицинским изделием (МИ) и не СППВР.
   * Формулировки вывода строятся как **прямые цитаты** документов Минздрава РФ. Предписывающий тон (*«вам необходимо принять X»*) запрещен.
   * В системе **отсутствует хранение персональных данных** (ФИО, паспорта, история болезни конкретных людей). Вся обработка сессионная в ОЗУ.
5. **Командный Git-регламент:**  
   * Запрещены прямые коммиты в `main`.
   * Ветки именуются по стандарту: `feat/<название>`, `fix/<название>`, `data/<название>`.
   * Коммиты строго по Conventional Commits: `feat(парсер): текст`, `fix(граф): текст`.
   * Папки `.venv/`, `data/raw/`, `*.parquet`, `.env` заблокированы в `.gitignore`.
6. **Воспроизводимость ГРЛС:** raw HTTP-ответы сохраняются без изменения байтов; очистка и исправление кодировки выполняются только в ETL. Основной справочник строится только из `Д`/`П`. Признак полноты обязан иметь область `coverage_scope`: проверка Д/П не означает выгрузку всех состояний реестра. Локальные отчёты и `data/processed/backups/` исключены из Git; код, тесты и описание проверенных результатов версионируются.

### 6.1. ГРЛС: источник, политика статусов и контракт данных

**Источник:** публичный API `https://rlp.minzdrav.gov.ru/medicine/portal/api/v0.1/medicament-registry`. Авторизация, cookies и токены браузера не используются. Базовый загрузчик не задаёт фильтр статусов автоматически; специальный сборщик `grls_active.py` явно передаёт повторяющиеся `conditionIds=Д` и `conditionIds=П`.

**Политика основного справочника:** включать `Д` («Действующий») и `П` («Действует, на подтверждении государственной регистрации»). `П` отличается от `ПП` («Приостановлено применение»). `ИЗМ`, `ИСКЛ`, `ИСТ`, `ПП`, `ЕАЭС` и остальные состояния не входят в текущую выбранную область. `ИЗМ` не приравнивается автоматически к недействующей регистрации; исключение отражает выбранную политику данных. Старые смешанные результаты сохранены в локальных резервных копиях. Сопоставление названия с МНН/АТХ само по себе не является клинической рекомендацией или подтверждением допустимости назначения.

**Сбор и проверка полноты:**

- Python 3.11+, async httpx, последовательные страницы с `page=1`, `size=100`; паузы и retry для 429/5xx/сетевых ошибок.
- В большой выборке API после первых 10000 объектов наблюдались записи без lpId/торгового названия/АТХ и нестабильный x-total-count за концом выборки. Прямая пагинация не подтверждает полноту.
- `grls_active.py` разбивает Д/П по поддерживаемым фильтрам `entryDateStart`/`entryDateEnd`. Текущие границы — 2024-01-01 и 2025-01-01; при изменении размеров частей их можно задать через повторяющийся `--split-date`.
- Размеры полученных частей: 6013 + 4027 + 6545 = 16585. Проверены завершение каждой части, принадлежность статусов Д/П, непустые lpId, совпадение числа уникальных lpId с общим счётчиком до и после загрузки и суммой размеров частей.
- Итоговый snapshot публикуется только при успешной сверке. `complete=true`, `coverage_verified=true`, `coverage_scope=conditionIds=Д,П` означают покрытие этой выборки относительно API на момент выгрузки. `registry_complete=false`: все состояния ГРЛС не выгружены.
- Ответы и контрольные запросы сохраняются в `data/raw/grls/collection_active_*/`, итог — в `data/raw/grls/snapshot_*/pages/`. Тела ответов копируются побайтово с проверкой SHA-256; manifest хранит происхождение каждой страницы. Старые raw-выгрузки не удаляются.

**ETL и схема:**

| Файл | Контракт |
|---|---|
| `data/processed/grls_normalized.parquet` | `trade_name_norm`: String; `inn_norm`: String; `atx_code`: List(String) |
| `data/processed/grls_normalized_records.parquet` | `lp_id`, `ru_number`, исходные/исправленные названия, массивы `mnn_codes`/`atx_codes`, `condition_id`, `release_forms_json`, `source_snapshot`, `source_page` |
| `data/processed/grls_normalized_report.json` | Область и проверка покрытия, число входных записей, пропущенные страницы, отсутствующие поля и итоговые связи; локальный файл |

Pydantic v2 валидирует структуру, Polars приводит названия к нижнему регистру, удаляет дозировки/распространённые формы/скобочные фрагменты, нормализует пробелы и дедуплицирует связи. pandas не используется. `mnnName="~"` становится отсутствующим значением; исходный текст остаётся в raw. Несколько МНН и АТХ не схлопываются до одного кода и не разворачиваются в неподтверждённые пары. Колонки `atx_name` в основном справочнике нет.

`--repair-mojibake` включает проверяемое обратимое исправление подозрительных строк только на ETL-слое. `--mapped-only` включает в поисковый Parquet только заполненную связь торговое название → МНН → АТХ. Страницы без единой пригодной связи пропускаются с отчётом; смешанные страницы не отбрасываются целиком. Некорректный JSON или неизвестная схема блокируют запись результата. `--allow-incomplete` нужен только для явно принятого неполного источника. `--additional-input-dir` позволяет объединять snapshot, но не используется для подмешивания других статусов в основной справочник Д/П.

**Проверенный результат от 16.10.2026:** snapshot `snapshot_20261016T133330279379Z`, 168 страниц, 16585 уникальных записей (16517 Д, 68 П). Все 16585 сохранены в таблице происхождения. Из них 15125 (91.2%) имеют заполненную связь; 1460 исключены из поисковой таблицы из-за отсутствующих полей. После дедупликации получено 9364 связи. Счётчики отсутствующих торгового названия (110), МНН (966) и АТХ (648) пересекаются. Число уникальных связей не является процентом покрытия регистрационных записей.

**Воспроизведение:**

```bash

SSL_CERT_FILE="$HOME/Downloads/Russian_Trusted_CA.pem" python -m src.nlp.grls_active --delay 1

# Сборщик напечатает путь нового проверенного snapshot; текущий результат:
python -m src.nlp.grls_etl --input-dir data/raw/grls/snapshot_20261016T133330279379Z --repair-mojibake --mapped-only

python -m pytest -q
```

Проверки находятся в `tests/test_grls_pipeline.py`, `tests/test_grls_integration.py`, `tests/test_grls_active.py`. Основные сценарии используют мокированный HTTP и не скачивают реестр. Они проверяют пагинацию/фильтры, retry, повторы/пустые/повреждённые ответы, отказ от ложной полноты, несколько кодов, очистку, сохранность raw, воспроизводимость и сохранение прежнего результата при ошибке. Медицинская правильность каждой связи независимо тестами не устанавливается. Подробности диагностики: `docs/grls_api_diagnostics.md`, анализ статусов: `docs/grls_status_analysis.md`, команды и результаты: `README.md`.

#### Спринт 3 (Недели 11–16): Сквозной MVP и первый запуск

* `feat(graphrag)`: Cypher-экстрактор подграфа: выгрузка цепочек несовместимости для пары (Диагнозы, Лекарства).

### 2-й СЕМЕСТР: Мультиагенты, полипрагмазия и научный эксперимент

#### Спринт 4 (Недели 1–5): Архитектура Multi-Agent Debate (MAD)
* `feat(agents-mad)`: Реализация стейт-машины дебатов в LangGraph:
  * `SafetyAgent`: строгий поиск противопоказаний и токсичности;
  * `EfficacyAgent`: защита терапевтической пользы, корректировка дозировок, поиск альтернатив;
  * `ClinicalArbiter`: протокол вычисления консенсуса (до 3 раундов).
* `feat(ddi)`: Алгоритмический анализ межлекарственных взаимодействий (DDI) при одновременном приеме 3+ препаратов.
* `feat(owl)`: Экспорт онтологии в стандартный формат OWL/RDF через `owlready2` для валидации в Protégé.

#### Спринт 5 (Недели 6–11): Бенчмаркинг и оценка устойчивости
* `data(benchmark)`: Формирование контрольного датасета из 50 сложных клинических ситуаций (коморбидные пациенты).
* `test(ragas)`: Автоматизированный замер метрик качества через фреймворк Ragas:
  * **Faithfulness** (фактологическая точность цитирования графа, таргет: $\ge 98\%$);
  * **Context Recall** (полнота найденных противопоказаний).
* `test(ablation)`: Сравнительный эксперимент: Предлагаемый GraphRAG против Vanilla RAG (поиск без графа) и чистого ChatGPT.
* `ui(graph)`: Интерактивная 3D-визуализация путей противопоказаний в Streamlit (`pyvis` / `st-link-analysis`).

#### Спринт 6 (Недели 12–16): Оформление диплома и защита
* Подготовка аналитических отчетов и выгрузка результатов экспериментов в таблицы и графики.
* Оформление пояснительной записки диплома (3 независимые исследовательские главы):
  * Глава 1: Методы извлечения и нормализации медицинских сущностей из клинических рекомендаций (NLP).
  * Глава 2: Онтологическое моделирование транзитивных фармакологических ограничений в графовых базах данных.
  * Глава 3: Мультиагентные системы верификации назначений и состязательная оценка их устойчивости.
* Финальный прогон демонстрационного стенда и защита проекта.
