# ГРЛС в Neo4j

Основной импортёр читает готовый **`grls_normalized.parquet`**: одна уникальная
комбинация `trade_name_norm`, `inn_norm`, набора `atx_code` создаёт один `GRLSDrug`.
Разные регистрационные номера, упаковки и версии записи не размножают лекарство
в основном поиске. Разные МНН и наборы АТХ остаются разными комбинациями.

Подробный `grls_normalized_records.parquet` импортируется отдельно с `--records`
для сохранения источников. HTTP-запросов импортёр не делает, raw не изменяет.

## Модель и ключи

```text
(GRLSDictionary {name: 'main'}) ─ CONTAINS → (GRLSDrug {drug_id, trade_name_norm, inn_norm, atx_code})
                                              ├─ HAS_TRADE_NAME → (TradeName)
                                              ├─ HAS_INN        → (INN {key: 'name:…'})
                                              ├─ HAS_ATC        → (ATC)
                                              └─ SUPPORTED_BY  → (GRLSRecord)

Отдельные источники:
(GRLSRegistration {lp_id})
    └─ HAS_RECORD → (GRLSRecord {record_id, content_hash, source_snapshot, source_pages, ...})
                         ├─ HAS_TRADE_NAME → (TradeName {name_norm})
                         ├─ HAS_INN        → (INN {key, code ИЛИ name_norm})
                         └─ HAS_ATC        → (ATC {code})
```

`drug_id` — SHA-256 названия, полного МНН и отсортированного уникального набора
АТХ. Он не зависит от `lpId`. Импорт справочника выполняется одной транзакцией,
включая обновление связей `CONTAINS`; неактуальное членство удаляется без удаления
наблюдений или клинических связей. Ошибка не оставляет частично заменённый справочник.
Справочники с другими именами не изменяются.

Коды МНН отсутствуют в normalized Parquet: основной узел МНН хранит полное имя,
без автоматического приписывания ему кодов. Коды и исходные поля доступны в
регистрационных источниках. `link_dictionary_sources` прикрепляет уже загруженные
источники через `SUPPORTED_BY` только при совпадении всей нормализованной связи.

`GRLSRegistration` — стабильная регистрация с уникальным `lp_id`. Две регистрации
с одним торговым названием остаются разными регистрациями. Регистрационный номер
`ru_number` сохраняется в наблюдении и не используется как уникальный ключ.

`GRLSRecord` — подтверждение из конкретного снимка. Его `record_id` — SHA-256
канонического JSON-массива `[source_snapshot, lp_id]`. Поэтому новый снимок
добавляет подтверждение к существующей регистрации. Один снимок не затирает
предыдущий. Значение `source_snapshot` берётся из ETL без изменения; для повтора
нужно сохранять исходный идентификатор снимка внутри Parquet. Перемещение самого
Parquet его не меняет.

Страницы — локаторы: повтор одного наблюдения на другой странице добавляет
элемент в `source_pages`, а не новый узел. Полные исходные и очищенные названия,
коды, форма выпуска в JSON, статус и `ru_number` остаются на `GRLSRecord`.
Таким образом, каждая связь от наблюдения имеет источник: снимок, страницы и
регистрацию. Исходные строки сохраняются в `*_raw`, преобразования не меняют raw.

Ключ торгового названия — `normalize_trade_query` существующего `DrugResolver`:
регистр и знак товарного знака убираются, номер дозировки сохраняется. Названия
с разными дозировками не объединяются. Нечёткое сопоставление не выполняется.

МНН имеет два пространства ключей:

- `code:<mnn_code>` для кода из ГРЛС;
- `name:<normalize_query(mnn_name)>`, если кодов нет, но есть полное название.

Общее `mnn_name` хранится на наблюдении. Оно **не приписывается каждому коду**,
не делится по `+` и не используется для автоматического объединения кодовых и
именных узлов. Это не утверждение о соответствии отдельных кодов отдельным
веществам. `~` и пустое имя означают отсутствие названия. Коды МНН при этом,
если они даны, сохраняются независимо.

АТХ идентифицируется кодом без внешних пробелов в верхнем регистре. Пустые и
повторные элементы массивов убираются. Иерархия АТХ из кодов не выводится.

Если источник содержит МНН `[M1, M2]` и АТХ `[A1, A2]`, создаются четыре связи
**от наблюдения**, а не четыре пары `МНН → АТХ`. Позиции элементов массивов не
считаются соответствием. Прямые связи `INN → ATC` импортёр не создаёт.

## Повтор, обновления и ошибки

У узлов справочника и источников есть ограничения уникальности; импорт использует `MERGE`.
Повтор того же файла не создаёт узлы или связи. Повтор страницы также не
дублирует `source_pages`. Для проверки доступны счётчики `nodes_created` и
`relationships_created` — при повторе они равны нулю.

Содержание наблюдения защищено `content_hash`: изменения полей под той же парой
`source_snapshot/lp_id` считаются конфликтом. Противоречащие друг другу строки
одного входного файла выявляются до записи. Конфликт с уже загруженным
наблюдением вызывает ошибку ограничения уникальности и откат текущего пакета.
Для новых сведений используйте новый идентификатор снимка. Если требуется
исправление ошибочного старого импорта, оно должно быть отдельной явной миграцией.

До первой записи в Neo4j весь вход проверяется Pydantic v2:

- записи без непустого `lp_id` пропускаются и считаются в `skipped_missing_id`;
- статусы, отличные от Д/П/ИЗМ, пропускаются и считаются в `skipped_status`;
- `ИЗМ` сохраняется как исходный статус, без приравнивания к Д/П;
- структурные ошибки, отсутствие столбцов, снимка или страницы блокируют импорт;
- отсутствие МНН или АТХ не мешает сохранить остальную пригодную запись.

Каждый пакет выполняется одной управляемой транзакцией с безопасным повтором.
Счётчики обновляются после успешного завершения транзакции. Общей транзакции
на весь файл нет: при сбое ранее подтверждённые пакеты остаются в базе.
Повторный запуск безопасно продолжает загрузку.

Импорт добавляет метки и ограничения ГРЛС. `ICD10`, `PARENT_OF`, их свойства и
существующий загрузчик МКБ-10 не изменяются.

## Запуск

Из корня проекта с активированным окружением Python 3.11+:

```bash
# Проверка файла без Neo4j и без .env:
python -m src.graph.grls_loader --dry-run

# Загрузка уникального справочника с параметрами NEO4J_* из локального .env:
python -m src.graph.grls_loader --batch-size 1000

# Прикрепить уже загруженные регистрационные источники:
python -m src.graph.grls_loader --link-records data/processed/grls_normalized_records.parquet

# Отдельный импорт регистрационных источников:
python -m src.graph.grls_loader --records --batch-size 1000

# Другой файл регистрационных источников и база:
python -m src.graph.grls_loader --records --input data/processed/example_records.parquet --database neo4j
```

Результат — JSON-отчёт: число входных и уникальных пригодных наблюдений,
повторов, пропущенных строк, подтверждённых пакетов, созданных узлов и связей.
`imported_records` отражает число уникальных связей справочника либо наблюдений
в режиме `--records`, включая существующие; новые объекты считаются отдельно.
Логи пакетов выводятся в stderr. Отчёт не записывается в репозиторий автоматически.

`.env`, исходные выгрузки, Parquet и локальные отчёты в Git не включаются.

## Контракт поиска

```python
from src.graph.connection import graph_db
from src.graph.grls_search import GRLSGraphResolver

resolver = GRLSGraphResolver(graph_db.driver)
try:
    result = resolver.search("Торговое название")
    # Источники и ограничение конкретным снимком:
    # evidence = resolver.search_records("Торговое название", source_snapshot="идентификатор")
finally:
    graph_db.close()
```

Просмотр основного справочника в Neo4j Browser:

```cypher
MATCH (:GRLSDictionary {name: 'main'})-[:CONTAINS]->(drug:GRLSDrug)
WHERE drug.trade_name_norm = 'конкор'
RETURN drug.trade_name_norm AS trade_name,
       drug.inn_norm AS inn_name, drug.atx_code AS atx_codes
```

Основной ответ `GRLSDictionarySearchResult` расширяет `DrugSearchResult`:

- `query`, `matches`, `ambiguous` сохраняют назначение;
- каждое совпадение содержит `trade_name`, `inn`, `atx_codes`;
- дополнительно возвращается стабильный `drug_id`;
- одинаковая связь возвращается один раз, независимо от количества источников.

`search_records` возвращает подробный `GRLSDrugSearchResult` с `lp_id`, `ru_number`,
`record_id`, `mnn_codes`, `source_snapshot`, `source_pages`. В нём источники остаются
отдельными наблюдениями. `source_snapshot` ограничивает именно этот метод.
Наличие в справочнике не утверждает актуальность регистрации на текущую дату.

Поиск поддерживает точное нормализованное торговое название, варианты с номером
дозировки при запросе без дозировки и точное полное МНН. Он переиспользует функции
нормализации существующего `DrugResolver`; нечёткий поиск и медицинские выводы
не входят в этот контракт. `ambiguous` определяется разными парами
`(trade_name, inn)`, как в текущем поиске по Parquet.

## Проверки

```bash
# Без подключения к базе:
python -m pytest -q tests/test_grls_graph.py tests/test_grls_dictionary.py tests/test_grls_resolver.py

# С настроенными NEO4J_* и запущенным Neo4j:
RUN_NEO4J_TESTS=1 python -m pytest -q tests/test_grls_neo4j.py tests/test_grls_dictionary_neo4j.py tests/test_icd10_neo4j.py
```

Интеграционные тесты используют случайный префикс для синтетических записей,
удаляют только созданные ими данные и не очищают базу. Проверяются повторный
импорт, независимые массивы кодов, происхождение страниц, изоляция снимков,
откат пакета при конфликте и сохранность всех узлов/связей МКБ-10. Ограничения
схемы остаются установленными. Для старого набора тестов МКБ-10 требуется заранее
загруженная иерархия.
