# Работа с клиническими утверждениями без модели

Эти команды не вызывают LLM, не читают настройки API и не подключаются к Neo4j.
Нужны установленные зависимости проекта, подготовленные страницы КР и справочник
ГРЛС. Raw-файлы не изменяются.

Основной процесс автоматический. Вручную проверяется небольшая эталонная
выборка для оценки качества. Просмотр человеком каждого утверждения всего
массива не требуется. Отдельная ручная проверка выбранных записей доступна
как дополнительная возможность.

## Подготовить проверку нашей выборки

```bash
python -m src.nlp.clinical_offline prepare --output-dir data/processed/clinical_trials/offline_check
```

По умолчанию используется `tests/clinical_reference_28_3.json` — готовая разметка
пяти выбранных утверждений. Это повторная обработка разметки, а не извлечение
отношений моделью. В отчёте указывается `source_kind: reference_annotations`.

По умолчанию создаётся `claims.json`. Файл ручной проверки создаётся только
по явному запросу:

| Файл | Содержимое |
|---|---|
| `claims.json` | Исходный контекст, утверждения, цитаты, позиции, контрольные суммы, варианты поиска ГРЛС, статусы и причины ошибок |
| `reviews.json` | Необязательный черновик; создаётся только с `--review-draft` |

Каталог должен быть новым. Для повторного запуска укажите другое имя.
Результаты в `data/processed/clinical_trials/` исключены из Git.

Для ранее сохранённого результата `clinical_trial` добавьте `--input <файл.json>`.
Другие страницы и справочник задаются через `--pages` и `--dictionary`.
Сведения ГРЛС из входного JSON не считаются проверенными: поиск выполняется заново.

Результат сохраняется сразу, без одобрения человеком. Статус `auto_checked`
означает, что автоматические проверки пройдены и лекарства сопоставлены.
Он не означает медицинскую достоверность. Ошибки доказательств получают
`disputed`, неразрешённые названия — `unresolved`. Эти записи также сохраняются
со своими причинами, а не превращаются в обязательную очередь ручной работы.
Поле `manual_review` по умолчанию равно `not_requested`.

## Что проверяется автоматически

- Документ и страница однозначно присутствуют в Parquet.
- Подготовленный фрагмент дословно находится на этой странице.
- Цитата имеет однозначное расположение во фрагменте. При различиях только
  в пробелах и переносах строк она заменяется дословным фрагментом источника.
- Названия участников присутствуют в цитате. Для названий допускается различие
  регистра и пробелов, но не раскрытие групп или подбор синонимов.
- Каждое указанное условие присутствует в цитате; допускаются различия
  только в пробелах и переносах строк.
- Названия лекарств сопоставлены существующим поиском ГРЛС.
- Явные утверждение и отрицание для одинаковых участников и одинаковых условий
  получают спорный статус. Для известных лекарств сравниваются МНН;
  для заболеваний — названия из текста, без предположений о синонимах.

Позиции символов `quote_start` и `quote_end` относятся к тексту сохранённого фрагмента.
Конечная позиция не включается. `text_sha256` позволяет обнаружить изменение
контекста. `page_quote_start` и `page_quote_end` относятся ко всей исходной
странице, а `page_sha256` фиксирует её полный текст. Изменение страницы
аннулирует прежнее решение проверки, даже если сама цитата сохранилась.
Исправленные метаданные документа не скрывают исходную ошибку:
при несовпадении сохраняется `original_source` и выставляется `disputed`.

Основные причины проблем:

| Причина | Значение |
|---|---|
| `source_mismatch` | Ответ указывал другой документ, страницу или расположение |
| `quote_not_found` | Цитаты нет в тексте |
| `ambiguous_quote` | Цитата встречается несколько раз; позиция не выбирается наугад |
| `subject_not_in_quote`, `object_not_in_quote` | Название участника не подтверждается цитатой |
| `condition_not_in_quote` | Указанного условия нет в цитате |
| `uncertain_statement` | Утверждение содержит сомнение |
| `contradictory_polarity` | Для одинаковых участников и условий есть утверждение и отрицание |
| `subject_not_found`, `object_not_found` | Лекарство не найдено |
| `subject_ambiguous`, `object_ambiguous` | Название неоднозначно; варианты сохранены |
| `subject_missing_inn`, `object_missing_inn` | Найденная запись не содержит МНН |

Пропущенное условие, неправильное отрицание или ошибочный медицинский смысл
нельзя надёжно установить одним поиском строк. Это остаётся задачей сравнения
с эталоном и ручной проверки. Код не меняет `polarity` и не придумывает условия.

## Сравнить с эталоном

```bash
python -m src.nlp.clinical_offline compare --report data/processed/clinical_trials/offline_check/claims.json
```

Для каждого выбранного примера выводится `matched`, `different` или `missing`.
Сравниваются участники, тип связи, отрицание и условия; спорные результаты
не засчитываются совпадениями. Выборка частичная: прочие найденные утверждения
не считаются ошибками автоматически. Описания могут отличаться по формулировке.
Названия сравниваются строго, кроме регистра и пробелов: синонимы и падежные
формы нужно оценить отдельно.

Сравнение готовой разметки с самой собой не измеряет качество LLM.
Для этого позже потребуется отчёт из настоящего ответа модели.

## Необязательная ручная проверка выбранных записей

Этот дополнительный путь нужен, если отдельные выбранные связи нужно явно
подтвердить человеком. Он не нужен для массового извлечения, сохранения
результатов, сравнения с эталоном или демонстрации автоматических проверок.

Для небольшого выбранного набора добавьте к `prepare` флаг `--review-draft`.
Только тогда появится `reviews.json`, а `manual_review` будет `not_reviewed`.
Решения по умолчанию — `pending`. После фактической проверки выбранной записи
доступны `confirmed`, `disputed`, `rejected`. Для такого подтверждения нужны:

- `reviewer` — имя или идентификатор проверяющего;
- `reviewed_at` — дата и время с часовым поясом, например `2026-11-17T12:00:00+07:00`;
- `pdf_checked`, `participants_checked`, `polarity_checked`, `conditions_checked` —
  значение `true` только после соответствующей проверки;
- `icd10_code` для противопоказания — код заболевания, выбранный проверяющим
  и существующий в справочнике МКБ-10. Блоки и классы МКБ-10 не принимаются.

Пока проверка не выполнена, поля менять не нужно. Глобальные отметки о проверке
эталонной выборки в исходном JSON также не меняются автоматически.
Команда ниже относится только к этому дополнительному пути:

```bash
python -m src.nlp.clinical_review --report data/processed/clinical_trials/offline_check/claims.json --reviews data/processed/clinical_trials/offline_check/reviews.json --output data/processed/clinical_trials/offline_check/export.json
```

С нетронутым черновиком экспорт содержит только отложенные записи.
При подтверждении источник и поиск ГРЛС проверяются заново. Любая правка
утверждения, контекста или разрешения имени меняет идентификатор и требует
новой проверки. Непроверенные, спорные, отклонённые, неразрешённые и отрицаемые
связи не попадают в списки подтверждённых противопоказаний или взаимодействий.
Отрицание сохраняется в исходном отчёте; отсутствие противопоказания не создаёт
ребро `CONTRAINDICATED_FOR`.

Файл ручного экспорта содержит `contraindications`, `interactions` и `deferred`.
Подтверждённые записи соответствуют моделям существующего чекера, сохраняют
источник, условия и сведения о ручной проверке. Это локальный экспорт;
записи в базу графа команда не выполняет. Существующие файлы не перезаписываются.
Неверное подтверждение вызывает ошибку, а не молчаливый пропуск.
Автоматическое присвоение медицинского статуса `confirmed` из статуса
`auto_checked` не выполняется. Правила использования автоматически извлечённых
связей в графе нужно определять после оценки качества модели на эталоне.

## Тесты

```bash
python -m pytest -q tests/test_clinical_*.py tests/test_grls_resolver.py
```

Тесты работают без API и Neo4j. Локальные PDF и Parquet нужны только для тестов,
которые сверяют настоящие исходные файлы; при их отсутствии эти тесты пропускаются.
